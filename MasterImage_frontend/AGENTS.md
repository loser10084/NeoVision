# AGENTS.md

## 1. 项目定位
本项目是“放疗影像智能勾画助手”前端，服务对象为放射科/放疗科医生。界面需强调：
- 医疗场景的专业可信
- 信息层级清晰、可快速决策
- 高频操作低认知负担
- 多端一致性（uni-app 场景）

## 2. 本轮改造目标
- 目标类型：仅 UI 与布局升级
- 风格来源：参考 `Image.png` 的视觉语言（配色、层级、卡片组织、留白、圆角、图标语气），不复制具体元素
- 主色调：淡蓝医疗风（低饱和、低对比刺眼度）
- 质量要求：视觉统一、交互可达、移动端可读性优先

## 3. 硬性边界（必须遵守）
- 不修改接口定义、请求路径、请求方法、入参/出参结构
- 不修改业务流程与页面跳转逻辑
- 不新增或删除后端依赖
- 不改变认证机制、token 存取、权限判断行为
- 不重构数据模型与字段语义
- 不在本轮引入与 UI 改造无关的功能

## 4. 现有技术与目录约定
- 技术栈：uni-app + Vue（项目以页面 SFC 为主），组件方案不受限（可用原生 uni 组件、自定义组件或第三方组件）
- 关键目录：
- `pages/`：业务页面（auth / patient / agent / model）
- `common/`：接口封装与请求逻辑（仅可读，不改行为）
- `static/`：静态资源
- `App.vue`、`uni.scss`：全局样式与主题入口
- 约束：
- UI 改造优先通过样式系统、布局层与组件外观完成（以视觉效果最优为准）
- 不要求必须使用 `wot-design-uni`，可在不改变接口与流程前提下自由选择更优 UI 实现
- 非必要不改 `common/api.js`、`common/request.js`

## 5. 视觉与体验规范（淡蓝医疗风）
- 色彩：
- 主色：医疗淡蓝系（用于主按钮、激活态、重点状态）
- 中性色：高可读灰阶（正文、辅助文本、边框、分割线）
- 状态色：成功/警告/错误保持医疗场景克制，不使用高荧光
- 组件：
- 统一圆角体系（卡片、输入框、按钮、标签）
- 卡片化信息分组，减少硬分割线堆叠
- 统一阴影策略（弱阴影、少层级）
- 排版：
- 标题/正文/辅助文案三级层级稳定
- 列表与表单间距网格化（避免“忽大忽小”）
- 关键数据字号优先保证可读性
- 交互：
- 点击区域满足移动端最小触控尺寸
- 加载、空态、错误态视觉一致
- 禁止仅靠颜色表达状态，需配合文本/图标

## 6. 页面改造优先级（默认全页面）
- P0：登录/注册、患者列表、患者详情
- P1：GTV 初稿、CTV 外扩、CTV 精修、热力图相关页
- P2：AI 会话入口与对话页、我的页面
- P3：模型查看页与细节统一

## 7. 流程规范（固定执行）
- Step 1（code）：在现有代码中完成可运行的 UI 初稿（不动接口）
- Step 2（figma）：将关键页面映射到 Figma，建立统一视觉稿
- Step 3（人工修改）：由设计/产品进行人工精修与确认
- Step 4（code）：将最终视觉规范回填代码，完成一致化落地
- Step 5（playwright 自检）：调用 `skills/playwright-ui-self-check/SKILL.md` 执行页面级回归与控制台错误检查，前端语法/模板错误必须修复并复检通过

## 8. Figma 协作要求
- 每次改造先明确页面范围、状态覆盖（默认/加载/空/错误）
- 设计输出必须标注：颜色、字号、间距、圆角、阴影、组件状态
- 回填代码时建立可复用 design token（颜色/间距/圆角/阴影）
- 若设计稿与当前交互冲突，优先保持业务流程不变，再做视觉适配

## 9. 代码实施约束
- 可修改：
- 页面模板结构（仅布局层面）
- 页面 scoped 样式
- `App.vue`、`uni.scss` 的主题变量与全局视觉规则
- 可新增：
- 纯样式类、设计 token、UI 复用片段
- 禁止：
- 修改 API 调用函数签名与返回处理
- 变更导航路由路径与核心流程控制
- 将 UI 改造与业务重构混在同一提交

## 10. 验收标准（UI 改造通过条件）
- 视觉统一：全站主色、圆角、间距、组件风格一致
- 可用性：核心流程可完整走通（登录->患者->分割相关页面）
- 稳定性：接口请求与数据回显行为与改造前一致
- 兼容性：主流移动端视口无明显布局错位、文字溢出可控
- 完整性：加载/空态/错误态均有统一表现
- 自检通过：Playwright 控制台无前端编译/语法错误（如 `Element is missing end tag`、`Unexpected token`、`Unterminated string`）

## 11. 提交与变更管理
- 提交粒度：按页面或模块拆分，避免超大混合提交
- 提交说明需包含：
- 改造页面范围
- 是否影响接口（必须为“否”）
- 视觉规范变更点（色彩/间距/组件）
- 若发现必须改接口才能实现的需求：停止实现，先提评审，不得直接修改

## 12. Playwright 自检规范（必做）
- 统一入口：使用 Skill `playwright-ui-self-check`（路径：`skills/playwright-ui-self-check/SKILL.md`）
- 触发时机：任何 UI、布局、样式、文案、页面结构修改后必须执行
- 默认检查页面：
- `/pages/agent/chat`
- `/pages/agent/conversation`
- `/pages/patient/list`
- `/pages/patient/detail`
- 本次改动涉及的其它页面（如 `gtv-draft`、`ctv-refine`、`ctv-expand`、`ctv-heatmap`、`auth/*`）
- 失败处理：
- 若为前端语法/模板错误：必须先修复再复检，直到错误清零
- 若为后端联调错误（如 CORS、接口 5xx）：标记为“环境问题”，不作为 UI 改造阻塞项，但需在结果中说明
